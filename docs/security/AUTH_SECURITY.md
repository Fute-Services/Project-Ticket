# Auth/Session Security — Findings New to This Pass

For the full auth design (cookies, JWT, refresh rotation, CSRF, caches), see `docs/07-authentication.md` — it is thorough and this file does not repeat it. This file adds only what that doc doesn't already cover, cross-referenced against it.

No code changed. No new live login/auth requests were made in this pass beyond the two already-documented, non-auth-limiter-consuming CORS/header checks in `SECURITY_HEADERS.md` (an unauthenticated `OPTIONS` and an unauthenticated `GET /api/auth/me`, neither of which touches `authLimiter` since that limiter is scoped to `/login`, `/register`, `/refresh`, `/verify-password` only, per `main/backend/routes/authRoutes.js`).

## 1. Cookie transport correctness — deployment-topology risk already flagged, worth restating here

`docs/07-authentication.md` documents `isDeployed = Boolean(process.env.VERCEL)` deciding `secure`/`sameSite` on all three cookies. `docs/20-deployment.md` independently flags that on the actual self-hosted `192.168.1.23` backend, `process.env.VERCEL` is presumably unset, which would produce `SameSite=Lax`, non-`Secure` cookies — and since the Vercel-hosted frontend calling this backend is cross-origin, a `SameSite=Lax` cookie would not be sent on those requests at all, which would break login/session persistence outright for anyone using the Vercel frontend against the self-hosted backend.

This is not a new finding — it's already tracked in `docs/20-deployment.md` as "worth verifying." Restated here because it is squarely an **auth security correctness** question (a misconfigured `SameSite` here isn't just a functional bug, it's the same knob that keeps the CSRF/cross-origin-cookie design in `docs/07-authentication.md` §2 sound in the first place) — if the fallback ever silently becomes `SameSite=None` without `Secure` in some environment, that would be a real cross-site request weakness, not just a broken feature. Given the backend is reached over plain HTTP today (`http://192.168.1.23:5000`, confirmed in `SECURITY_HEADERS.md`), `Secure` cookies (`SameSite=None; Secure`) could not be sent over that connection anyway — so whichever branch is actually active, something in this picture needs the backend behind TLS to be fully correct. Not independently re-verified live in this pass (would require an authenticated login and cookie inspection, which the task explicitly asked to avoid re-triggering); flagged for a dedicated check outside the shared rate limit.

## 2. `verify-password` re-auth endpoint shares the login rate-limit bucket — already fixed for `/refresh`, still true for this one

`docs/07-authentication.md` notes `POST /api/auth/verify-password` is rate-limited "identically to login/register (10 requests / 15 min per IP) specifically because a stolen JWT would otherwise let an attacker brute-force the account's real password here with no throttle at all." This is intentional and correct as designed — flagged here only to note it is **not** part of the already-fixed `refreshLimiter` split (`docs/testing/BUGS_FOUND.md` BUG-01): `/refresh` got its own limiter because it isn't a credential-guessing surface, but `/verify-password` deliberately still shares the tight bucket with `/login`/`/register` because it *is* one. No action needed — this is confirmation that the fix was scoped correctly, not a new gap.

## 3. Password reset / creation flows — no new gap found beyond the documented length-only policy

`docs/15-security.md` already documents the length-only (10 char minimum) password policy as a known weakness. Nothing new was found in `superAdminUserController.js`'s `resetUserPassword`/`createUser` beyond what's already documented — no additional bypass, no missing role gate (both are `role('superadmin')`-gated per `docs/08-authorization.md`).

## 4. Session fixation / logout completeness

Read `authController.js`'s `logout` again with a session-security lens: it revokes the session server-side (`sessions/{sid}.set({revoked:true})`) and clears all three cookies. One thing worth noting that isn't a bug but is worth being explicit about: revocation take-up-to-30-seconds via the cache described in `docs/07-authentication.md` §"Why the caches exist" applies here too — a logout on one tab doesn't invalidate an already-issued, still-valid (in cache) access token on another device holding the *same* session until that cache window elapses or a new request re-checks `isSessionRevoked`. This is the same tradeoff already documented in `docs/15-security.md`'s "Potential Weaknesses," not a new independent finding — restated here specifically in the logout context since that's the moment a user would most expect immediate effect.

## 5. No auth-related dependency CVEs found — confirmed with a live `npm audit`

`docs/19-dependencies.md` documents the `overrides` block pinning `jose` and `qs` to specific minimum versions for what it infers is a supply-chain hygiene reason. `jsonwebtoken@^9.0.2` and `bcryptjs@^2.4.3` (the two auth-critical packages) are both current major versions with no outstanding known-CVE version ranges. This was cross-checked against the existing dependency doc **and** confirmed with a fresh `npm audit --omit=dev` run against `main/backend/package-lock.json` in this pass (no login/rate-limit budget required — this is a local dependency-tree check, not a live HTTP request): it reports **0 critical/high** vulnerabilities. It does report one **moderate**, unrelated-to-auth finding — `exceljs`'s transitive `uuid` dependency — logged as `VULN-06` in `VULNERABILITIES_FOUND.md` rather than here, since it has nothing to do with the auth/session code this file covers.
